# コードレビュースキル

このスキルは、プルリクエストのレビューを行う際に使用します。レビューの役割を絞ることを最優先にし、モデルの性能ですでに賄える一般的な観点までルール化しません。

## When to Use

- プルリクエストへのレビュー指摘を出すとき
- CI経由、またはレビュー専用のサービス経由で自動レビューを行うとき
- レビュー観点をプロジェクト固有のルールに絞りたいとき

## Instructions

### レビューの役割を絞る

一般的な観点（命名、重複、基本的なエラーハンドリングなど）は、モデルの性能にすでに含まれています。これをわざわざルール化すると、指示が長くなるだけで、かえって精度を落とします。

このスキルでは、次だけをルールとして渡します。

- そのプロジェクト固有の設計判断（なぜこの方式を選んだか）
- チーム固有の命名規則・ディレクトリ規約
- 過去に繰り返し指摘された、そのプロジェクト特有の落とし穴

### レビューの手順

1. 差分を読み、変更の範囲がSub-issueの指示文の範囲内かを確認する
2. プロジェクト固有のルール（AGENTS.md、docs、このSKILLの参照ファイル）と照らして、外れている箇所を指摘する
3. 一般的な品質観点（可読性、命名など）は、明らかな問題がある場合のみ指摘し、好みの範囲には踏み込まない
4. 指摘には深刻度をつける

### 出力の型

```text
指摘1: (深刻度: 高/中/低)
該当箇所: (ファイル・行)
内容: (何が、どのルールに反しているか)
```

### 落とし穴の追記

同じ指摘が繰り返し出た場合は、汎用ルールとして書くのではなく、`pitfalls.md`のような参照ファイルにそのプロジェクト固有の落とし穴として書き足します。汎用的なコーディング規約は、このSKILLの対象外です。

## よくある問題

### 一般的な指摘ばかりで、プロジェクト固有の問題を見落とす

命名や重複のような一般的な指摘に紙面を使うと、そのプロジェクトでしか通用しない設計判断からの逸脱を見落としやすくなります。プロジェクト固有のルールとの整合性を優先して確認します。

### ルールを増やしすぎて指示が長くなる

指摘が増えるたびにルールを追記すると、指示文が肥大化し、かえって精度が落ちます。実際に再発した指摘だけをルール化します。
