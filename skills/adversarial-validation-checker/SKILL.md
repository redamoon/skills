# 敵対的検証チェッカースキル

このスキルは、実装に入る前のSub-issue指示文を、実装するエージェントとは別の立場で疑い、指摘する際に使用します。指示文を書いたエージェント自身に検証させると、自分の書いた前提を疑いにくいため、検証は別のセッション・別のエージェントに任せます。

## When to Use

- Sub-issueの指示文を、実装に入る前に検証してほしいと依頼されたとき
- 「敵対的検証して」「反証を試みて」と依頼されたとき
- レビュー・チェッカーの役割で、指示文や仕様の甘さを指摘するとき

## Instructions

### 検証の姿勢

このスキルを実行するエージェントは、次を守ります。

- なぜその指示文になったかの説明は求めない。指示文だけを見て判断する
- 「問題なし」という結論を早く出さない。指摘が0件の場合は、確認した観点をすべて書き出す
- 会話の文脈（それまでのやり取り）は使わない。指示文単体で読んで判断する

### 確認する4つの観点

1. **範囲**: 1PR・1Sub-issueに収まっているか
2. **やらないことの漏れ**: 範囲に近い作業で、明記されていないものがないか
3. **ファイル境界**: 触ってよい/いけないファイルの境界が明確か。責務を越える書き方がないか
4. **完了条件**: 機械的に確認できる形か。感覚的な表現（「正しく動く」「問題ない」）が残っていないか

### 出力の型

指摘には、深刻度と根拠を必ずつけます。

```text
指摘1: (深刻度: 高/中/低)
内容: (何が問題か)
根拠: (指示文のどの部分がそう読めるか)
```

指摘が0件の場合も、4つの観点それぞれについて「問題なし。根拠: ...」と書きます。無言で「問題なし」だけを返しません。

### 指摘への対応

指摘を受けた側は、指示文を直接書き換えず、指示文自体を更新してから、指摘が出なくなるまで検証を繰り返します。検証と実装は別の役割のまま維持します。

## よくある問題

### 検証が「問題なし」だけで終わる

検証エージェントの最大の失敗モードは、ろくに確認せずに合格を出すことです。4つの観点それぞれに根拠を書かせることで、この失敗を防ぎます。

### 指示文を書いたエージェントがそのまま検証してしまう

同じ会話・同じエージェントが検証すると、自分の前提を疑えません。検証は別セッション、別エージェントに渡します。
