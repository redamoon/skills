# コードからの仕様抽出

既存コードを読み、根拠付きの仕様書を作る。言語に依存する知識は `references/` にあり、手順そのものは言語非依存。

## When to Use

- 仕様書が無い・古いシステムの振る舞いを、コードを正として文書化したいとき
- 「この機能の仕様をまとめて」「この画面の仕様を起こして」と依頼されたとき
- 改修・移行・リプレイスの前に、現行の業務ルールや画面の振る舞いを洗い出したいとき
- 前回抽出した仕様書を、コードの変更に合わせて差分更新したいとき

## 原則(必ず守る)

1. **事実と推測を分ける**: コードから直接読み取れることは「事実」、意図や背景の推定は「推測」として明示的に区別する。推測を事実として書かない。
2. **根拠を必ず付ける**: 仕様の各項目に `path/to/file.ext:行番号` を付ける。根拠を示せない項目は書かない。
3. **機械で取れる事実はスクリプトで取る**: ルート一覧・画面一覧・スキーマ・依存関係などは、読んで推測する前にスクリプトや既存ツールで取得する。
4. **分からないことは「未確認」とする**: 埋めずに「未確認事項」に積む。

## 構成

- `scripts/detect_stack.py`: 言語・フレームワークの判定と、読むべき参照ファイルの提示
- `scripts/grep_entrypoints.py`: エントリポイント候補を `file:line` 付きで列挙
- `scripts/dep_graph.py`: import/use を解析し、モジュール依存をMermaid図＋根拠表で出力
- `scripts/screen_inventory.py`: フロントエンドの画面一覧、画面ごとの事実(API・フォーム・状態分岐・遷移)、画面遷移図を出力
- `references/stacks/*.md`: 言語・フレームワーク別の読み方(対応: typescript-node, python, java-spring, go, ruby-rails, php-laravel, csharp-dotnet, perl, frontend-react, frontend-vue, _generic)
- `references/mermaid.md`: 図の種類(依存図・画面遷移図・ER図・シーケンス図・状態遷移図)と描き方のルール
- `templates/module-spec.md`: モジュール仕様の出力テンプレート
- `templates/screen-spec.md`: 画面仕様の出力テンプレート

スクリプトはすべて Python 3 の標準ライブラリだけで動く。

## 手順

### Step 1. スタックを特定する

```bash
python3 scripts/detect_stack.py <対象ディレクトリ>
```

出力された言語・フレームワーク・ビルドツールを確認し、該当する `references/stacks/<名前>.md` を読む。該当ファイルがない場合は `references/stacks/_generic.md` を読み、必要ならその言語向けの参照ファイルを同じ形式で追加することをユーザーに提案する。

複数言語が混在する場合(例: TypeScriptのフロント＋Goのバックエンド)は、それぞれの参照ファイルを読み、サブシステムごとに分けて扱う。Next.js・Nuxt・Remix のようなフルスタックのフレームワークは、画面側(`frontend-*`)とサーバ側(`typescript-node`)の両方を読む。

### Step 2. 範囲を決める

ユーザーに抽出範囲を確認する(指定がなければ提案して合意を取る)。

- リポジトリ全体 / 特定モジュール / 特定機能(例: 請求締め処理) / 特定画面
- 出力する仕様の種類: 機能仕様 / API仕様 / 画面仕様 / データモデル / 業務ルール / バッチ・ジョブ / 外部連携

大きいリポジトリでは、いきなり全体を読まない。まずモジュール一覧(画面があれば画面一覧も)を作り、優先順位を合意する。

### Step 3. 事実を機械的に集める

参照ファイルの「機械的に取れる情報」に従い、以下を収集して `spec-work/facts/` に保存する。

- エントリポイント一覧(HTTPルート、CLIコマンド、ジョブ、イベントハンドラ、キューコンシューマ)
- 画面一覧(フロントエンドがある場合)
- データモデル(マイグレーション、ORMモデル、DDL、スキーマ定義)
- 外部連携(HTTPクライアント、SDK呼び出し、メッセージング)
- 設定値・フィーチャーフラグ・環境変数
- 既存のテスト一覧(テスト名は仕様の宝庫)

汎用の補助として:

```bash
python3 scripts/grep_entrypoints.py <対象ディレクトリ> --stack <参照ファイル名(拡張子なし)>
```

`--stack` には Step 1 で示された参照ファイル名(例: `typescript-node,go`)をカンマ区切りで渡す。結果は正規表現による候補なので、必ず実コードで確認する。

OpenAPI生成、`rails routes`、`php artisan route:list` のようにフレームワーク公式のコマンドが使えるなら、そちらを優先する。

モジュール依存はここで機械的に取る:

```bash
python3 scripts/dep_graph.py <対象ディレクトリ> --prefix <ソースのルート> --depth <階層>
```

出力(Mermaid図＋根拠表)は `spec-work/facts/module-deps.md` に保存する。ノードが多すぎる/粗すぎる場合は `--depth` を調整する。Step 2 のモジュール一覧づくりにも使える。

フロントエンド(`frontend-react` / `frontend-vue`)があれば、画面もここで機械的に取る:

```bash
python3 scripts/screen_inventory.py <対象ディレクトリ>                    # 画面一覧 → spec-work/facts/screens.md
python3 scripts/screen_inventory.py <対象ディレクトリ> --transitions      # 画面遷移図 → spec-work/facts/screen-transitions.md
python3 scripts/screen_inventory.py <対象ディレクトリ> --screen <ルート>  # 1画面の事実 → spec-work/facts/screens/<画面名>.md
```

画面一覧は Step 2 で優先順位を決める材料にもなる。`--screen` は Step 4 で画面ごとに実行する。

### Step 4. エントリポイントから処理を追う

エントリポイントごとに、呼び出しを下へたどって以下を読み取る。

- 入力(パラメータ、バリデーション条件、必須/任意、型、制約)
- 処理の流れ(分岐条件、状態遷移、トランザクション境界)
- 出力(レスポンス、更新されるテーブル・カラム、発行されるイベント)
- エラー(例外の種類、エラーコード、リトライ)
- 権限(認可チェックの場所と条件)

**業務ルール**は特に丁寧に拾う。条件分岐の定数、計算式、丸め処理、日付・締め日の扱い、ステータスの遷移条件は、そのまま仕様になる。

テストコードがあれば対応するテストを読み、期待値から仕様を裏付ける。テストと実装が食い違う場合は「未確認事項」に記録する。

**画面**は、`screen_inventory.py --screen` の出力(追跡したファイルと事実の表)を起点に、以下を読み取る。

- アクセス条件(ガード・ミドルウェア・ロールによる出し分け)
- 表示項目(データの出どころ、書式、表示条件)
- 状態(読み込み中・空・エラー・成功・権限なし)。コード上の表示分岐を根拠にし、コードに無い状態は作らない
- 入力項目とバリデーション(スキーマを正とし、画面側の制約と食い違えば未確認事項へ)
- 操作(ハンドラ → API → 結果)と遷移先

画面から呼ばれる API は、バックエンドのエントリポイントと突き合わせて相互にリンクする。

### Step 5. モジュール・画面単位で書く

`templates/module-spec.md` に沿って、モジュールごとに `spec-work/modules/<モジュール名>.md` を作る。画面は `templates/screen-spec.md` に沿って `spec-work/screens/<画面名>.md` に1画面1ファイルで作る。1ファイルが長くなりすぎたら機能単位でさらに分割する。

図は `references/mermaid.md` を読んでから描く。モジュールごとに、該当するものを入れる。

- データを持つ → ER図
- 主要な処理フロー、外部連携がある → シーケンス図
- ステータスを持つエンティティがある → 状態遷移図

大規模な場合はモジュール・画面ごとに並列に処理してよい(サブエージェントが使える環境なら活用する)。その場合も原則1〜4は全員に守らせる。

### Step 6. 統合する

モジュール別・画面別の仕様から全体を組み立てる。

- `specs/README.md`: システム概要、モジュール一覧、画面一覧、モジュール間の依存(`dep_graph.py` の図を埋め込む)
- `specs/screens/`: 画面仕様(README の画面一覧からリンクする)
- `specs/diagrams/`: 全体図(`module-deps.md`: モジュール依存図、`screen-transitions.md`: 画面遷移図、`er.md`: 全体ER図)
- `specs/glossary.md`: 用語集(コード上の名前と業務用語・画面上の文言の対応)
- `specs/open-questions.md`: 未確認事項の一覧(誰に確認すべきかの見当も添える)

### Step 7. 自己点検する

出力前に確認する。

- [ ] すべての項目に `file:line` の根拠があるか
- [ ] 「推測」が「事実」の欄に混ざっていないか
- [ ] 根拠の行番号を数件ランダムに開き、実際に書かれた内容と一致するか
- [ ] Step 3 で集めたエントリポイントと画面が漏れなく仕様に載っているか(件数を突き合わせる)
- [ ] 図の各要素に根拠があり、推測の関係が点線になっているか
- [ ] Mermaid が描画できるか(`npx -y @mermaid-js/mermaid-cli -i <file>.md -o /tmp/out.md` が使える環境なら実行する。使えなければ ID の記号・予約語 `end` を目視確認)

## 再抽出(差分更新)

既存の `specs/` がある場合は全体をやり直さない。`git diff --name-only <前回の基準コミット>` で変更ファイルを出し、影響するモジュール・画面だけ Step 3〜7 をやり直す。画面は共通コンポーネントの変更でも影響を受けるので、`screen_inventory.py --screen` の「追跡したファイル」に変更ファイルが含まれる画面を対象にする。各仕様ファイルの先頭に、抽出時のコミットハッシュを記録しておく。
