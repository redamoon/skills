# X ポスト文案作成（x-algorithm 準拠）

## When to Use

- X 向けのポスト・スレッド・引用リポストの文案を書く・推敲するとき
- ブログ記事やメモから X 用の要約投稿を作るとき
- 「For You に載りやすい」「アルゴリズムを意識した」投稿文案が欲しいとき

## 前提（アルゴリズムの要点）

[xai-org/x-algorithm](https://github.com/xai-org/x-algorithm) によると、For You フィードは次の流れで決まる。

1. **候補取得**: フォロー中（Thunder）＋ ML 類似検索（Phoenix Retrieval）
2. **スコアリング**: Grok ベースの Transformer が各アクション確率を予測
3. **最終スコア**: `Final Score = Σ (weight × P(action))`
4. **フィルタ**: 古い投稿・重複・スパム/ポリシー違反などを除外

**重要**: 手作りの特徴量は使わず、**ユーザーの過去エンゲージメント履歴**から関連性を学習する。キーワード詰め込みより「読者が実際に反応する内容」を優先する。

詳細は [reference.md](reference.md) を参照。

## ワークフロー

### Step 1: 入力を確認

ユーザーから以下を確認（不足なら質問する）:

| 項目 | 例 |
|------|-----|
| 目的 | 記事告知 / 意見表明 / 議論開始 / 実績共有 |
| 素材 | ブログ URL、メモ、箇条書き、なし |
| 形式 | 単発 / スレッド / 引用リポスト |
| トーン | カジュアル / 専門的 / 挑発的（控えめ） |
| 文字数 | 280字以内 / 長文スレッド |

### Step 2: スコアリング観点で設計

ポストは次の**正のアクション**を引き出すよう設計する（重みは非公開だが、複数アクションを同時に狙う）:

| アクション | 文案での狙い方 |
|-----------|---------------|
| reply | 質問・二択・「あなたなら？」・議論の余地 |
| repost / quote | 引用しやすい結論1行・意外性・共感フレーズ |
| favorite | 共感・「わかる」・保存したくなる要点 |
| click / dwell | 続きが気になる構成・スレッド・リンク先の価値 |
| profile_click / follow_author | 専門性・一貫したテーマの提示 |
| video_view / photo_expand | 図解・スクショ・短尺動画の添付提案 |
| share | 実用性・「誰かに送りたい」情報 |

**避ける（負のアクション）**: スパム感、釣りタイトル、過激表現、同一内容の連投（Author Diversity で減衰）、古い話の蒸し返し。

### Step 3: 文案を書く

#### 単発ポストの型

```
[フック: 1行で止める]
[本体: 具体例・数字・経験]
[CTA: 質問 or 次のアクション]
```

#### スレッドの型

```
1/ 結論またはフック（単独で repost/quote できる1文）
2/ 背景・問題
3/ 具体例 or 手順
4/ 学び・反論余地
5/ まとめ + 質問（reply 誘導）
```

#### 記事告知の型

```
[読者の悩み] → [記事で得られること] → [URL]
※ URL は末尾。本文だけで価値が伝わるように書く（click 以外の反応も狙う）
```

### Step 4: チェックリスト

出力前に確認:

- [ ] 最初の1〜2行だけで意味が通るか（タイムライン流し読み想定）
- [ ] reply または quote のフックがあるか
- [ ] スパム・誇大・ポリシー違反っぽい表現がないか（Grox フィルタ想定）
- [ ] 280字制限（単発の場合）を超えていないか
- [ ] ハッシュタグは0〜2個（本文の自然さを優先）
- [ ] 同一テーマの連投前提なら、各ポストが独立した価値を持つか
- [ ] メディア添付を推奨する場合、その理由を添えたか

### Step 5: チャットで草案を提示

ユーザー確認・修正を経て確定稿に近づける。チャット上の形式:

```markdown
## 推奨案（メイン）
[文案]

## 代替案
[文案]

## 添付メディア案（任意）
- 画像/動画の内容提案

## 設計メモ
- 狙うアクション: reply, repost, ...
- 根拠: （例）冒頭を quote 向けに独立させた
```

### Step 6: 成果物ファイルを出力（必須）

文案が確定したら（またはユーザーが「ファイルに保存して」と依頼したら）、**必ず Markdown ファイルに書き出す**。チャットへの表示だけで終わらせない。

#### 保存先の確認（必須・都度）

**デフォルトの保存先は設けない。** ファイルを書き出す前に、毎回ユーザーに保存先を確認する。

1. 次のように質問する: **「どこに保存しますか？保存先のディレクトリまたはファイルパスを指定してください。」**
2. ユーザーがパスを返すまで、ファイルの作成・書き込みを開始しない
3. **ディレクトリのみ**指定された場合: 下記の命名規則でファイル名を提案し、保存してよいか確認してから作成する
4. **ファイルパスまで**指定された場合: そのパスをそのまま使う。既存ファイルがあるときは、上書きか別名かを確認する
5. 同一セッションで複数回保存するときも、毎回パスを確認する（「前回と同じ場所でよいですか？」と聞いてもよいが、無言では前回のパスを使わない）

#### ファイル命名

```
x_{YYYYMMDD}_{テーマ}_{campaign}[_{形式}].md
```

| 部分 | 例 | ルール |
|------|-----|--------|
| `YYYYMMDD` | `20260606` | 投稿予定日または作成日 |
| `テーマ` | `エンジニアリング戦略` | 20字以内・記事タイトルから短縮 |
| `campaign` | `1日目` | 連投キャンペーン時のみ。なければ省略 |
| `形式` | `スレッド` / `単発` | 省略可 |

#### frontmatter

[templates/x_post.md](templates/x_post.md) に従う。

| フィールド | 必須 | 値 |
|-----------|------|-----|
| `title` | ✅ | 人間が読むタイトル |
| `type` | ✅ | `x-post` 固定 |
| `format` | ✅ | `single` / `thread` / `quote` |
| `status` | ✅ | `draft` / `ready` / `posted` |
| `source` | 推奨 | 元記事・素材のファイルパス |
| `source_url` | 任意 | note / はてな等の公開 URL |
| `campaign_day` | 任意 | 連投の何日目か（数値） |
| `scheduled_date` | 任意 | `YYYY-MM-DD` |
| `hashtags` | 任意 | YAML 配列 |
| `target_actions` | 任意 | `reply`, `quote` 等 |
| `posted_at` | 任意 | 投稿後に記入 |

#### 本文構成

ファイル内は次の順序で書く。

1. **`## コピペ用（確定稿）`** — X にそのまま貼れる本文のみ（設計メモを混ぜない）
2. **`## 文字数`** — 単発は280字チェック表。スレッドは各ポストの文字数表
3. **`## 設計メモ`** — 狙うアクション・切り口・根拠
4. **`## 添付メディア案`** — 任意
5. **`## 代替案（未使用）`** — チャットで出したが採用しなかった案
6. **`## 投稿後メモ`** — 空欄で残す（投稿後にユーザーが記入）

#### 更新 vs 新規

| 状況 | 操作 |
|------|------|
| 新規キャンペーン | 新ファイル作成 |
| 同一キャンペーンの別日 | 別ファイル作成（`2日目` 等） |
| 既存文案の推敲 | 同一ファイルを上書き更新。`status` は `draft` のまま |
| 投稿完了 | `status: posted`、`posted_at` を記入 |

#### 完了報告

ファイル保存後、チャットで次を返す。

```markdown
## 保存しました

- ファイル: `{ユーザーが指定したパス}`
- 形式: スレッド（6ポスト）
- status: draft

### 次のアクション
- [ ] 文案を X にコピペ
- [ ] 投稿後 `status: posted` に更新
```

## 執筆ルール

### やること

1. **1ポスト1メッセージ** — 情報を詰め込みすぎない
2. **具体 > 抽象** — 数字・固有名詞・失敗談で dwell を稼ぐ
3. **会話を開始する** — アルゴリズムは reply を高く評価しうる
4. **引用可能な1文を作る** — quote repost 向けの punch line
5. **テーマの一貫性** — Phoenix Retrieval はエンゲージメント履歴と類似検索。ニッチを維持すると OON リーチに有利
6. **鮮度** — タイムリーな話題・今週の学び（AgeFilter 想定）

### やらないこと

1. **エンゲージメントベイトの明示** — 「いいねください」「拡散希望」
2. **キーワード羅列** — 手作り特徴量は廃止されている
3. **同内容の使い回し** — RepostDeduplication / Author Diversity
4. **釣り・ミスリード** — P(not_interested) を上げる
5. **スパム的連投** — 質より量は逆効果

## ブログ連携

ユーザーが指定したブログ記事や長文メモから X 文案を作る場合:

1. 記事の h2/h3 から **独立した切り口** を3つ抽出
2. 各切り口で別ポスト案を出す（Author Diversity 対策）
3. 長文記事はスレッド化。1ツイート目に記事の結論を置く
4. 保存時は Step 6 のとおり、都度保存先パスを確認する
