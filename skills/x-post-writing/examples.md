# X ポスト文案 例

## 例1: 技術記事の告知（単発）

**入力**: 「AGENTS.md についてのブログ記事を X で告知したい」

**推奨案**:
```
README は人間向け。AGENTS.md は AI エージェント向け。

Cursor / Claude Code で「毎回同じ指示を繰り返す」問題、
AGENTS.md にルールを書いておけばかなり減る。

うちのリポジトリではこう書いてる 👇
[URL]

みなさんの AGENTS.md、何を書いてますか？
```

**設計メモ**: reply（質問）、quote（冒頭2行）、follow_author（実運用の一貫性）、open_link（URL は減点ではない。本文だけで価値が伝わる）

## 例2: 学びの共有（スレッド）

**入力**: 「レガシーコード改善で学んだことをスレッドにしたい」

**推奨案**:
```
1/ テストがないレガシーコード、いきなりリファクタリングしない。

まず「変更したい1行」だけ特定して、そこを安全に動かす。
全部直そうとすると必ず壊れる。

2/ 手順は3つだけ覚えた:
・外側から観察（挙動を記録）
・最小の変更（1コミット1意図）
・動いたら止まる（次の変更は別 PR）

3/ 実例: 300行の関数を、最初は変数名1つだけ直した。
動いた。次は早期 return を1つ追加。これを2週間続けた。

4/ 「きれいなコード」より「壊れない変更」のほうが先。
きれいさは変更が積み上がってからでいい。

5/ レガシーコードと戦ってる人、最初の1変更は何にしましたか？
```

**設計メモ**: quote（1/ が独立）、reply（5/ の問い。相互フォローが返せる）、share_via_copy_link（手順が外へ持ち出せる）、follow_author（実例の一貫性）

## 例3: 意見表明（議論開始）

**入力**: 「エンジニアの意思決定の重要性について短く投稿」

**推奨案**:
```
コードを書く速度 < 何を作るか決める速度

技術選定で2週間悩むより、
「今週作らない機能」を1つ決めるほうがチームの生産性は上がる。

同意しますか？ それとも違いますか？
```

**設計メモ**: reply（二択。相互フォローが返しやすい）、quote（1行目）、favorite は副産物

## 例4: 避けるべき文案

**NG**:
```
【拡散希望】🔥🔥🔥
AI エージェント プロンプト エンジニアリング Cursor Claude
最新情報まとめ！必見！
いいね・RT よろしく 🙏
```

**理由**: スパム的、キーワード羅列、明示的ベイト → P(not_interested) / mute / report と visibility-filtering のリスク。favorite 狙いの拡散希望は重み的にも弱い

**改善案**:
```
Cursor で AI に毎回「テスト書いて」と言ってた。

AGENTS.md に「新規関数にはテスト必須」と書いたら、
3回に1回言うだけで済むようになった。

小さな1ファイル、効く。
```

## 例5: ブログ記事から3切り口

**入力**: 読書メモ記事「エンジニアリング戦略の作り方」

| 切り口 | 文案 |
|--------|------|
| 結論 | 「戦略がない」のではなく「言語化できていない」だけ、という本の一節が刺さった |
| 失敗談 | 技術的負債の優先順位、口頭で決めて半年後に全員忘れてた話 |
| 実践 | うちのチームで「やらないことリスト」を四半期ごとに更新してる理由 |

**設計メモ**: Author Diversity 対策で同一記事から別ポストを日を分けて投稿
