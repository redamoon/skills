# UX 思考 — 参照

`SKILL.md` の手順を回したあとに使う点検表と出力の型です。ここから入らず、仕事の特定と旅を先に終えます。

## 出力の型

チャットでは次の順で出します。画面案やコンポーネント案は、処方のあとです。

```markdown
## 仕事
- 誰:
- 状況:
- 終わらせたい変化:
- 成功の瞬間:
- 制約:

## 旅（出来事）
1. きっかけ:
2. 期待:
3. 最初の接触:
4. 最初の成功:
5. 迷いどころ:
6. 失敗したとき:
7. 完了の確認:
8. 完了後:

## 摩擦台帳
| 位置 | 種別 | 仕事が止まる理由 | 今の次の一手 |
|------|------|------------------|--------------|
|      |      |                  |              |

## 状態の穴
| 画面 | 空 | 読込 | 成功 | 部分成功 | 入力エラー | システムエラー | 権限 | 中断 |
|------|----|------|------|----------|------------|----------------|------|------|
|      |    |      |      |          |            |                |      |      |

## 処方（優先度）
1. 削る:
2. 並べ替える:
3. 足す:

## 検証の問い
- 何が起きれば、この設計が当たっていると言えるか
- 誰に、どの仕事で、何回試せば十分か
```

不足がある項は空欄のまま創作せず、ユーザーへ確認します。

ファイルへ書き出すときは、保存先を都度確認します。デフォルトの保存先は設けません。

## 摩擦台帳の記入例

仕事：「週末に、家族の予定を一件だけ確定したい」

| 位置 | 種別 | 仕事が止まる理由 | 今の次の一手 |
|------|------|------------------|--------------|
| 初回ホーム | 認知摩擦 | 「ワークスペースを作成」が予定の確定に見えない | 社内概念の作成 |
| 作成フォーム | 入力摩擦 | チーム名・タイムゾーンを、予定の前に聞かれる | 持っていない値の入力 |
| 保存後 | 待ち摩擦 | 保存中の表示がなく、押したか分からない | もう一度押すか待つ |
| バリデーション | 回復摩擦 | エラーで入力が消え、日付を入れ直す | 最初から入力 |

この例の処方は、「ワークスペース作成」を足すことではありません。空のカレンダーに「予定を入れる」を主ボタンにし、チーム名は最初の成功のあとに送ることです。

## 状態インベントリ

画面またはステップごとに一行。`—` は「この状態は起きない」ではなく「未設計」です。起きないと言えるときだけ `n/a` にします。

| 画面 / ステップ | 空 | 読込 | 成功 | 部分成功 | 入力エラー | システムエラー | 権限不足 | オフライン・中断 |
|-----------------|----|------|------|----------|------------|----------------|----------|------------------|
| 例: 予約フォーム | 日付未選択時の次の一手 | 空き確認中 | 確定済みの内容 | 一部日程だけ確保 | フィールド横の直し方 | 再試行 / 電話 | 代理予約の頼み方 | 下書き再開 |

点検の質問:

- 空状態は、最初の成功への入口になっているか（失敗の報告だけで終わっていないか）
- 読込は、待てばよいか止めればよいかが分かるか
- 部分成功を、全部失敗として扱っていないか
- 入力エラーとシステムエラーで、原因の帰属が入れ替わっていないか
- 中断後に、どこまで残っているか言えるか

## 次の一手の点検

各画面・ダイアログ・通知について、次に即答できなければ未回収の迷いです。

- [ ] 今、何の仕事の途中か分かるか
- [ ] 次にやることは一つに見えるか
- [ ] 主操作の結果が、押す前に分かるか
- [ ] 主ボタンの文言が、メカニズムではなく結果の動詞か
- [ ] 副操作が主ボタンと競っていないか
- [ ] やったあと、仕事が前に進んだと分かるか
- [ ] 間違えた位置から、仕事へ戻れるか
- [ ] 同じ仕事に、同じ言葉が使われているか

## コピーの書き換え

| 弱い | 強い | 理由 |
|------|------|------|
| 送信 / 実行 / OK | 予約を確定する | 結果を名指す |
| データがありません | 最初の予定を入れる | 空を入口にする |
| エラーが発生しました | 通信に失敗した。もう一度試す / 入力を残したまま待つ | 原因と次の一手 |
| 不正な入力です | 終了時刻が開始より前になっている。終了をあとへずらす | 直し方がある |
| 本当に削除しますか？ | この予定を削除する。カレンダーから消え、元に戻せない | 結果を先に見せる |
| 直感的な操作 | （削除する） | 診断にもコピーにもならない |

## ヒューリスティック早見（補助）

仕事・旅・摩擦・状態を終えたあとの点検に使います。ここから設計を始めません。

| 見るところ | 問い |
|------------|------|
| システムの状態が見えるか | 読込・保存・失敗が、無言になっていないか |
| 現実の用語か | ユーザーが持っている呼び方か、社内モデルか |
| 操作の主導権 | ユーザーが止めて、戻して、やり直せるか |
| 一貫性 | 同じ仕事が、画面ごとに別の手順・別名になっていないか |
| ミスの予防 | 破壊的操作の結果が、実行前に見えるか。確認ダイアログ頼みになっていないか |
| 思い出しより認識 | 記憶に置かせず、今見える情報で次の一手が決まるか |
| 柔軟性 | 初めてと毎日で、同じ手数を強いていないか |
| 最小限 | 今の仕事に使わない選択肢・入力が主経路にあるか |
| 復旧 | エラーが直し方付きか。入力が消えないか |
| 助け | その場の一文で足りるか。概念解説を操作に混ぜていないか |

出典の枠組み: Nielsen の 10 heuristics、Norman の実行／評価の溝。このスキルでは、ヒューリスティックの充足そのものを成果にしません。

## 入口別の始め方

| 入口 | 最初にやること | やらないこと |
|------|----------------|--------------|
| 新規の機能要望 | 要望を仕事の文に翻訳する | 画面一覧から描く |
| 既存画面のレビュー | 現状を旅に当て、途切れを指す | 部品の好みから直す |
| 「使いづらい」という不満 | 不満が起きた仕事と位置を特定する | 一般論のヒューリスティックを列挙する |
| コピーだけ直してほしい | その文が指名している次の一手を確認する | トーンだけ整える |
| 競合や参考画面がある | 参考が解いている仕事を先に言う | レイアウトを移植する |

## 検証の問い（例）

設計が当たっているかは、見た目の賛否ではなく、仕事が終わるかで見ます。

- 初めての人が、説明なしで最初の成功まで到達するか
- 毎日使う人が、同じ設定を毎回やらされていないか
- 失敗（入力ミス、通信切れ、権限不足）から、同じ仕事に戻れるか
- 主ボタンを隠したとき、次の一手が残るか（残らないなら、コピーと配置に依存しすぎ）
- 用語を社内語から仕事の言葉に戻したとき、画面の役割が変わって見えないか（変わるなら、画面が都合側になっている）
